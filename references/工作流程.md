# 工作流程

> 五段式主循环 + 三个核心机制 + 目录归属。这是"活儿怎么流动"的详规。

---

## 需求理解与结果回应

这项约定适用于已接入项目的日常任务,也适用于初始化和交接。

- **开工时重述**:新任务、接手任务或目标实质变化时,先读必要上下文,在实质执行前用自己的话自然概括“用户希望达到什么结果、目前什么问题促使这项需求”,必要时补充本轮范围。一两句话为宜,不逐字复述用户原话,也不用固定套话或单独的表格。
- **按变化触发**:普通补充、进度询问、确认继续或连续小改动不重复开场。用户改变目标时以最新目标为准,只更新变化部分;仅整理已完成工作的交接时,直接在收尾回应原始目标,不虚构新执行任务。
- **清楚就继续**:重述不新增确认关卡。明确的需求按已有授权继续执行;只有关键歧义会改变结果、范围或授权时才提问。未明确的动机或目标标为推断,不替用户编造意图,已有必要审批仍按原规则执行。
- **收尾时回应**:保留现有六项交接字段,用“为什么”简述本轮工作对应的用户目标与原始问题,结合实际改动、产出和验证说明达到了哪里。目标未达到或未验证时如实交代,不把“做了工作”等同于“解决了需求”,也不整段重复开场重述。

例如,用户要在协作流程中补充需求重述,可以说:“我理解,你希望 Agent 先说明自己理解的目标和待解决的问题,让你及时发现理解偏差,并在完成后核对结果是否回应了需求。我会把它写进开工约定,并让收尾回应原始目标。”按实际任务组织语言,不把示例当成每轮必填模板。

## 五段式主循环(每个任务走一遍)

### ① 立项
填 `flow/charter.md`:目标 / 范围(做什么 + 不做什么)/ 约束 / 成功标准 / 角色。
这是所有 Agent 开工要读的第一份;模糊目标先在这里钉死。

### ② 拆解
出 `flow/plan.md`:里程碑 + 任务拆解(每个任务标:负责角色、输入、产出落哪、验收标准),你确认。
**计划即契约**——用户明确调整目标或范围,即授权相应的计划变更;先更新 `plan.md` 再执行,不重复确认同一事项。尚需用户决定的变更先确认。复杂任务先用 Plan 模式出书面计划。

### ③ 执行
每个终端一个角色,读对应任务卡 `flow/tasks/T<编号>-<描述>.md` 开工(文件名带编号+短描述,如 `T01-X-API接入.md`)。
- 可独立的任务并行(git worktree / branch 隔离)。
- 小步、勤检查点。知识与方案产出落到根级 `docs/`;代码落到对应子项目目录或单体项目的 `scripts/`·`src/`,别只留对话里。

### ④ 评审
交付前**换另一个模型评审**(Codex 审 Claude,或反之),结论写 `docs/` 或任务卡。PASS / FAIL 才算过门。
**铁律:审稿模型 ≠ 产出模型**——错误不相关,等于免费质量倍增。

### ⑤ 沉淀
最终回复前,先完成当前路径生效入口要求的业务专项收工检查,不扩大本轮授权;核对文档、进展、决策和问题记录后,在最终回复直接展示任务结果与交接。Codex Stop 静默放行,不等待其续跑,不在结果后追加“无需更新”;Claude Code 保留单次续跑兜底。详见 `hook机制.md`。

合并产出;归档完成的任务卡;决策写 `flow/decisions.md`;**问题 / 解决 / 死路 / 踩坑写 `flow/踩坑记录.md`**;从中提炼的禁区 / 心智按 `文档维护SOP.md` 写进 `AGENTS.md`。

## 项目边界与分层

先判断协作边界,再运行五段循环。多个代码文件夹不等于多个项目:

- **单仓多子项目**:前端、后端、落地页等共享一个总体目标和仓库时,只在根级维护一套 `flow/`、`docs/` 和 hook。任务卡用产出路径区分模块,例如 `frontend/src/...`、`backend/src/...`。
- **独立仓库**:有独立 `.git`、版本、发布或团队边界时,每个仓库各自运行完整循环;上层总控仓库只记录跨仓目标、契约和集成交接。
- **子模块**:只有独立职责的模块才需要局部规则入口;普通脚本、构建产物和工具目录不建入口。

单仓多子项目的详细判断、文档位置和结构见 `多子项目结构.md`。

## 核心机制

### A. 进展日志 = 接力棒(Agent 接力的最小单位)
位置:`flow/进展.md`,**append、新的放最上面**。每个 Agent 干完一棒在顶部加一条;**顶部那条 = 当前交接棒**(`AGENTS.md` 开工必读它)。
每条字段:**做了什么 / 为什么 / 怎么理解 / 产出 / 问题与解决 / 下一步**。
- 一身三用:**可复制**(整条喂别的 Agent)、**可回看**(append 留全历史,你扫一遍就知道每个 Agent 干了啥)、**能接力**(顶部即最新棒)。
- 收工时这条**既写进文件、也在回复中展示同一组事实**——用户当场看到 + 可直接复制;按下方输出约定排版,允许调整标题和路径写法。
- 决策 → `decisions.md`,坑 → `踩坑记录.md`,产物 → `docs/`·`scripts/`(只给路径)。
- **「出方案 → 对照实现」**:A 把方案写 `docs/specs/xxx.md`,进展条的"产出/下一步"带上该路径;B 顺路径打开方案照着实现,再写自己那条(实现中发现的缺口回填进方案)。

**铁律:只带「指针 + 增量」**——指向真实产出(给路径)+ 这一棒新增,**不重抄内容**;接手方要细节顺指针回源文件读。
(为什么是一个 append 文件,而不是 N 张卡或覆盖快照:N 张卡会堆爆;覆盖会丢历史、没法复制;append 一个文件 = 留历史 + 不爆 + 顶部即棒。)

#### 交接输出约定

- 默认直接显示单层 Markdown 列表,使用 `- **字段名**：内容`。列表与前后正文、文件中的日期标题之间留空行;每项以一两句为宜。回复中的交接只展示一份,与已有结果说明合并,不再重复贴相同摘要。
- 字段按上方顺序写。「为什么」回应用户目标与原始问题,实际达成程度结合改动、产出和验证说明;「怎么理解」只保留影响接手的假设或边界;「问题与解决」交代执行障碍、处理及必要验证,无问题写“无新增问题”,未解决或未验证如实写;「下一步」给具体动作,已完成就明确完成。不同字段各写其职责,不另增重复的需求字段。
- 文件保留日期、任务、执行者和可迁移的项目相对路径;回复可用一句结果引出列表,文件路径按当前客户端转成可点击链接,在 Codex 中使用真实绝对路径。两处事实与完成状态保持一致。
- 交接默认不整段包在代码块、引用块、表格、HTML 或客户端专属指令里。用户明确指定其他格式时按用户要求。规则只约定生成内容和 Markdown 结构,不保证各客户端字体、间距或容器外观相同。
- 已有项目定向更新当前入口与规范,历史进展保留原样;Codex Stop 静默放行,Claude Code 的兜底提醒沿用此约定,不另设展示格式。

### B. 分层入口 = 运行时合同
根级 `AGENTS.md` 是总体合同,写跨模块的精要规则、约束、目录地图和指针;根级 `CLAUDE.md` 软链到它。单仓多子项目中,每个有独立职责的模块再建局部 `AGENTS.md` + `CLAUDE.md` 软链,只补本模块职责、命令和约束。两个层级都保持同源,让 Claude Code 与 Codex 在对应目录读取一致规则。

局部入口不能另起总体计划。根级 `flow/` 管整体推进,根级 `docs/` 管统一文档,局部入口只把 Agent 导回这些真相源。

### C. 跨模型评审
Claude Code = 主控(持上下文 / 编排);Codex = 独立第二双眼睛。
模式:生成→评审 / 对抗找茬 / 第二意见。何时:每次交付前、高风险逻辑、设计岔路口。

## 目录归属(R1)
| 文件夹 | 放什么 |
|---|---|
| 根级 `flow/` | 唯一控制层:charter / plan(契约)/ 进展(append 日志,顶部=交接棒)/ decisions / 踩坑记录 / tasks / 规范副本 |
| 根级 `docs/` | 集中内容层:产品 / 架构 / `contracts/` 跨模块契约 / `modules/` 模块说明 / 评审与产出说明 |
| `<module>/`、`scripts/`、`src/` | 代码、测试、构建与运行配置;已有 README 或代码生成文档可就近保留 |
| 根级 `AGENTS.md` | 总体运行时合同(见机制 B) |
| `<module>/AGENTS.md` | 有独立职责子项目的局部合同;同目录 `CLAUDE.md` 指向它 |
| `DESIGN.md` | (可选)设计 / 创意决策 |

**判据**:协调 / 推进总体项目的 → 根级 `flow/`;需要统一发现的知识、方案和交付说明 → 根级 `docs/`;代码 → 对应子项目。默认不在子项目重复建 `flow/` 或 `docs/`。

控制层**指向**真实产出:任务卡 / 进展条里的"产出(路径)"可以是 `docs/...`、`frontend/src/...`、`backend/src/...` 等具体路径。已有局部 README、生成文档或必须跟代码同步的说明不强行搬家,但应从根级 `docs/README.md` 建索引。
